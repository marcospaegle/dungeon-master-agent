# Glossary

**Abstract base class (ABC)** — optional way to declare a port in Python; `@abc.abstractmethod` blocks instantiation of incomplete subclasses; duck typing/Protocols are alternatives (Ch 2)
**Adapter** — implementation behind a port; secondary/driven (repo, publisher) or primary/driving (entrypoints) (Ch 2, 4)
**Aggregate** — cluster of objects treated as one unit for data changes; root is sole entrypoint; consistency boundary (Ch 7)
**Anemic Domain** — anti-pattern from putting too much logic in the service layer (Ch 4)
**Application service** — service-layer function orchestrating a use case (Ch 4)
**Architecture tax** — budgeting cleanup inside feature work (Epilogue)
**Ball of mud** — system with uncontrolled dependencies (Intro)
**Bootstrap script** — composition root: defaults, init, DI, returns message bus (Ch 13)
**Bounded context** — boundary within which a model/term has one meaning (Ch 7)
**Choreography** — event-based flow replacing orchestration (Ch 8)
**Classical mapping** — SQLAlchemy mapping where ORM imports the model (Ch 2)
**Classic vs London-school TDD** — state-based with fakes vs interaction-based with mocks (Ch 3)
**Cohesion** — tightness of related elements; good locally (Ch 3)
**Command** — imperative message to one handler; fails noisily (Ch 10)
**Command Handler pattern** — Commands + Events + Message Bus (Ch 10)
**Composition root** — single place where dependencies are wired (Ch 13)
**Connascence** — taxonomy of coupling: execution, timing, name (Ch 11)
**Consistency boundary** — scope where invariants hold transactionally; aggregate or service (Ch 7, 11)
**Coupling** — inability to change A without B; harmful globally (Ch 3)
**CQRS** — separate read and write models/paths (Ch 12)
**CQS** — functions either modify state or answer questions (Ch 12)
**Dependency Inversion Principle (DIP)** — high- and low-level modules depend on abstractions; details depend on abstractions (Intro)
**Distributed Ball of Mud** — noun-based microservices with chatty synchronous coupling (Ch 11)
**Domain** — the problem you're solving (Ch 1)
**Domain event** — fact recorded by the model, past tense (Ch 8)
**Domain model** — business-logic layer as a map of the business process; free of infrastructure (Ch 1)
**Domain service** — stateless domain logic with no natural entity home; a function (Ch 1, 4)
**Duck typing** — port defined by method names/signatures (Ch 2)
**Edge-to-edge test** — service-layer test with fakes for I/O (Ch 3, 5)
**Entity** — domain object with long-lived identity; equality by identity (Ch 1)
**Event** — broadcast fact; fails independently (Ch 8, 10)
**Event storming / event modeling** — collaborative modeling techniques (Ch 9, Epilogue)
**Eventual consistency** — consistency across aggregates/services reached via events (Ch 8, 11)
**Fake** — working in-memory test implementation (Ch 2, 3)
**Functional Core, Imperative Shell** — pure logic core, thin I/O shell (Ch 3)
**Handler** — function that receives a command/event and its dependencies (Ch 9)
**High gear / low gear** — service-layer tests vs domain tests (Ch 5)
**Idempotency** — repeated handling yields same state; essential for retries (Epilogue, App. E)
**Invariant** — condition always true after an operation (Ch 7)
**Message bus** — dict from message types to handlers; routes work (Ch 8, 10)
**Mock vs spy vs stub** — interaction verifier / call recorder / canned answers (Ch 3)
**Optimistic concurrency** — assume no conflict; detect via version number; retry (Ch 7)
**Persistence ignorance** — model unaware of storage (Ch 2)
**Pessimistic concurrency** — lock first (`SELECT FOR UPDATE`) (Ch 7)
**Port** — interface between app and what it abstracts (Ch 2)
**Postel's law / Tolerant Reader** — liberal in, conservative out; read only needed fields (App. E)
**Preparatory Refactoring** — make the change easy, then make the easy change (Ch 9)
**Primitive obsession** — wrapping primitives in classes everywhere; skeptical in Python (Ch 9)
**Read model / view model** — query-optimized, possibly denormalized store (Ch 12)
**Repository** — in-memory-collection illusion over storage, `add`/`get` (Ch 2)
**Service layer** — orchestration/use-case layer; API of the domain (Ch 4)
**SKU** — stock-keeping unit (Ch 1)
**SRP** — one reason to change; no "and"/"then" in descriptions (Ch 8)
**Strangler Fig** — gradually replace a legacy system by intercepting events (Epilogue)
**Temporal coupling** — all parts must be up at once (Ch 11)
**Unit of Work (UoW)** — atomic-operation abstraction; context manager; gives repos; collects events (Ch 6, 8)
**Ubiquitous language** — shared business jargon in code and tests (Ch 1)
**Value object** — immutable, identified by data (Ch 1)
**Version number** — field changed on every aggregate write for optimistic locking (Ch 7)
**Walking skeleton** — minimal deployed system that just logs input (Epilogue)
